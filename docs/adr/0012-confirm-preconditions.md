# Confirm の前提条件と、満たせない理由の見せ方

Report を Confirm できるのは、**明細が 1 件以上あり、かつすべての明細が `approved`** のときだけです。満たさない場合はサーバー側で拒否し、`LinesNotFullyApproved` を返します。UI では確定ボタンを**非活性にしたうえで、満たせていない理由を出します**（明細 0 件・未承認 N 件・差し戻し N 件）。

## なぜ「明細 1 件以上」を明示的に足すか

「すべての明細が承認済み」という条件は、明細が 0 件のときに自動的に真になります。この条件だけを書くと、明細を 1 行も入れていない報告書が確定を通り、確定は不可逆なので中身の空な報告書が永久に残ります。回復手段は修正版を作ることだけになります。空集合の扱いを条件に書き忘れると業務が壊れる典型なので、条件として明示することにしました。

## なぜボタンを消さずに非活性にするか

ボタンを非表示にすると、管理者は「なぜ確定できないのか」を明細表から自力で探すことになります。この業務でユーザーが知りたいのは「押せるかどうか」ではなく「**あと何をすれば前に進めるか**」なので、残っている未承認・差し戻しの**件数**を確定ボタンの近くに出すことにしました。

**個々の差し戻し理由は、確定ボタンの横ではなく明細表のその行に出します。** 理由は「どの明細を直すか」と対になった情報なので、行から引き剥がして並べると、どれの話なのかを読み手が突き合わせることになります。ボタンの近くには「あと何件残っているか」、行には「この行の何が問題か」を置く分担です。

押せるようにしておいて失敗させる案は、無駄な失敗を踏ませるだけなので採りませんでした。

## 影響

- UI の非活性化は表示の都合であって防御ではありません。サーバー側の拒否が唯一の保証であり、両方を必ず実装します。
- 「未承認 N 件・差し戻し N 件」は明細から導出します。Report 側には持ちません（ADR-0007）。
