# 明細の承認は行ではなく「その時点の内容」に紐づく

営業が ReportLine を Approve したあと、管理者がその行の金額や案件名を編集した場合、承認は失われ、その行は未確認の状態に戻ります。承認は行そのものに貼られた永続ラベルではなく、レビューした内容に対する意思表示だと定義したためです。

承認を行に貼ったままにすると「営業が承認 → 管理者が金額を書き換える → 全明細が承認済みなので確定できる」という経路が成立し、取引先へ提出される書類として業務が破綻します。宣言した業務ルールが崩れないことが本課題の評価軸である以上、ここは緩めません。

## 影響

- 差し戻し対応で管理者が編集を重ねるほど確定は遠のきます。これは業務として正しい遠のき方であり、UI 側では「あと何件の再承認が必要か」を明示して補います。
- 「どの内容に対する承認だったか」を判定できる必要があります。承認時点の内容を行に持たせるか、内容の更新時に承認を落とすかは実装の選択ですが、外から見える振る舞いは同じです。

## 関連

**明細の削除は `draft` 中のみ可能とし、`in_review` 以降は禁止します。** 確認依頼後に削除を許すと「営業が差し戻した明細を管理者が消す → 指摘が対応されないまま消える → 残りが全部承認済みなので確定できる」という経路ができます。削除を禁止すれば、この穴を塞ぐための追加の機構は一切要りません。金額の訂正は編集（承認は落ちます）で、不要になった明細への対応はコメントでのやりとりで足ります。

差し戻しは Report のステータスにはしません。実際には「明細 A は承認済み・明細 B は差し戻し・明細 C は未確認」が同時に起こり、Report 側の単一のステータスでは表現すると嘘になるためです。一覧での「差し戻しあり」表示は明細から導出します。
