# 担当営業は ReportLine だけが持ち、Report 側には持たせない

「自分に関係する報告書」は、**自分が担当する ReportLine を 1 件以上含む Report** として導出します。Report にも担当営業を持たせて非正規化する案は採りません。担当という同じ事実を 2 箇所に持つと、明細の担当を付け替えたときに必ずずれるためです。

## 可視範囲

営業は関係する Report を**全体として閲覧できます**。自分の担当明細だけに絞り込んで見せることはしません。報告書の金額合計や他の明細が見えない状態で承認させると、承認が「自分の行の数字が合っているか」の確認に痩せてしまい、業務上の確認の意味をなさないためです。

一方で **Approve / Change Request は自分の担当明細に対してのみ**行えます。「見えるが触れない」を明細単位で表現します。

### 閲覧は系列単位（Revision 導入時に拡張）

**詳細の閲覧だけは Report 単位ではなく `series_id` 単位で判定します。** 系列のどれかの版で担当明細を持つなら、その系列の全ての版を読めます。

版ごとに判定すると、版の履歴に出ているリンクを踏んだ先で拒否されます。修正版で担当が付け替えられた場合と、修正版の明細がまだ揃っていない場合の 2 つで実際に起こります。営業から見て「担当を外れた」のか「まだ明細が入っていない」のかを確かめる手段が無くなり、待つ以外にできることが無くなります（[ADR-0009](./0009-revision-is-a-copied-report.md)）。

**一覧は広げません。** 一覧は「いま自分が確認すべきもの」を出す場所なので、担当明細を含む版だけに絞ったままにします。旧版から新しい版へは版の履歴で辿れます。

## 影響

- 一覧クエリは Report と ReportLine の join になります。この規模では無視できるコストです。
- 権限判定の単位が「Report に対するアクセス可否」と「ReportLine に対する操作可否」の 2 段になります。前者を通っても後者で弾かれる経路があることを、API とドメイン層の両方で明示します。
- 閲覧の相関副問い合わせが `reports` の自己結合になります（外側の `series_id` と突き合わせるため）。`reports_series_idx` が効きます。
