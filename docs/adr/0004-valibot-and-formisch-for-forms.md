# スキーマは Valibot、フォームは Formisch に統一する

**決定:** 入力検証は Valibot で 1 度だけ定義します。フォームは `@formisch/react` にそのスキーマをそのまま渡します。サーバー（Elysia JS の OpenAPI 写し）も同じスキーマを使います。

## なぜ Valibot か

同じ検証規則をクライアントとサーバーで二重に書くと、必ずずれます。ずれは「確定できないはずの入力が通る」といった業務ルールの穴になります。サーバー・フォーム・OpenAPI の定義箇所を 1 つにすることが、この課題で守りたい Single Source of Truth だと判断しました。Zod でも OpenAPI には写せますが、フォームに Formisch を使うため、Valibot に揃えました。
また、Zod は広く使われている一方で、パフォーマンス・バンドルサイズに懸念があったため、後発で採用実績も豊富な Valibot を採用しました。

## なぜ Formisch か

アダプタを挟まず、Valibot スキーマからフォーム構造を導けるためです。スキーマを見れば UI の形が分かるので、認知コストが下がると判断しました。SSoT（Single Source of Truth）をスキーマに置いたまま、フォーム側で形を再定義することがないため、型の二重管理と不整合が発生しないと考えました。

## 採らなかった案

- **TanStack Form + valibot アダプタ** — 実績はありますが、アダプタの分だけスキーマとフォームの型が2重管理となり、一致しないケースも簡単に発生し得ます。また、スキーマを見ても画面が復元できないため見送りました。
- **Zod** — ElysiaJS の写しは受けられますが、Formisch は Valibot 前提のため見送りました。

## 影響

- `@formisch/react` は `1.0.0-rc.0` です。フォーム層を薄くし、業務ロジックをフォームコンポーネントに書きません。
- 検証は境界（ユーザー入力・API 入出力）にだけ置きます。
