# 認証は署名付き Cookie のダミーログインにする

**決定:** 認証基盤は入れません。ログイン画面は seed 済みユーザーの一覧から選ぶだけです。選んだ `user_id` を**サーバー側の秘密鍵で署名した httpOnly Cookie** に入れ、Elysia の macro が毎リクエストで検証して `user` をハンドラに渡します。パスワードは扱いません。

## なぜ

課題は、ロールの切り替えを認証基盤・ダミーログイン・画面切替のいずれでもよい、と記載があります。
そのため、採点の「業務ルールの堅牢さ」が見ているのは、「営業が他人の明細を承認できないといった権限が、パスワードやセッションの正しさではなく、「サーバーで拒否されるかどうか」と見受けられました。
権限判定は API 側で行うので、その手前を本物の認証にするのはコストが肥大化するため、要件が許しているダミーログインを選択しました。

ただし Cookie の署名は残すようにしました。署名が無い `user_id` だと、ブラウザの開発者ツールで書き換えるだけで他人になれるためです。これはダミーログインではなく、サーバーが権限を見ていないのと同じ状態であるため、署名は Elysia の cookie 機能で補うようにしました。

## 採らなかった案

- **Better Auth** — 課題がダミーログインを許しており、権限判定はサーバー側で足りるので入れませんでした。
- **署名なしの Cookie / ヘッダでロール切替** — 実装は最短ですが、API を直接叩けば他人の担当明細を承認できます。宣言した権限設計が崩れるため見送りました。
- **画面上のロール切替トグルのみ（クライアント判定）** — 画面は切り替わっても、API を直接叩けば他人の担当明細を承認できます。宣言した権限設計が崩れるため見送りました。

## 影響

- `user` テーブルは自前で持ちます（`id` / `name` / `email` / `role`）。`role` は `admin` | `sales` です。認証基盤由来のテーブル（session / account / verification）はありません。
- seed は `user` へ直接 insert します。ハッシュもサインアップ経路も要りません。管理者 1・営業 2 です。
- `.env.example` には `DATABASE_URL` と `COOKIE_SECRET` のみです。`COOKIE_SECRET` の生成方法（`openssl rand -base64 32`）を README に書きます。
- README に「これは要件が許容するダミーログインであり、本番運用の認証ではありません」と明記します。面接で聞かれる前に、選んだ理由ごと書いておきます。
- 本番相当の認証へ差し替える場合、変わるのは macro の `resolve` の中身だけです。認可判定とドメイン層には触りません。
