# SQLite ではなく Docker 上の PostgreSQL を使い、ORM は Drizzle にする

**決定:** 永続化は PostgreSQL（`docker compose`）+ Drizzle とします。SQLite ファイルは使いません。

## なぜ PostgreSQL か

任意の深掘りとして、確定後の修正版フロー（版管理）を選びました。確定済みの報告書は書き換えず、修正版は別の報告書として作ります。そのとき崩してはいけないルールの例が、「同じ系列（初版から続く版の束）に、下書き・確認中の版は同時に 1 つまで」です。確定済み行への更新禁止も同種です。こうした条件をアプリの if 文だけに置くと、別経路の書き込みで通ります。PostgreSQL なら部分ユニークインデックスや CHECK、トリガとしてデータ層に書けるため、選びました。宣言した業務ルールが、コードレビューの注意力ではなく、DB が拒否することで守られると判断しました。

## なぜ Drizzle か

`drizzle-valibot` で検証スキーマを Valibot 一本にできるためです（[0013](./0013-eden-treaty-with-openapi.md)）。公式が推す `drizzle-typebox` だと TypeBox が二重になり、フォーム側の Valibot と検証規則が割れます。あわせて、生成 SQL に近く制約・トリガを ORM の裏に隠さない点も評価しました。

## 採らなかった案

- **SQLite（ファイル）** — 手数は最短ですが、部分ユニークやトリガの表現力で劣ります。上のルールを DB で拒否できないなら深掘りの意味が薄くなるため、見送りました。
- **Prisma** — 制約は書けますが、Valibot への導出と生 SQL 寄りの見え方が Drizzle より弱いと判断し、見送りました。

## 影響

- 採点者に Docker を要求します。再現手順は後で README に 1 コマンドへ畳みます（compose → migrate → seed）。
- seed には下書き・確認中・確定済み・修正版を最初から入れます。
