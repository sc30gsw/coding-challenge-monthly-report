# Revision は Report の複製として表す

確定済み Report に誤りが見つかったときの修正版は、履歴テーブルや専用の版テーブルではなく、**Report 行と ReportLine 行を丸ごと複製した新しい Report** として作ります。系列は `series_id`（最初の版の識別子）でまとめ、`version` で順序を持ちます。複製元は `superseded` になり、内容は不変のまま残ります。新しい版は `draft` から始まります。

ADR-0007 により、明細は版ごとに再編集され、承認され直す必要があります。版を読み取り専用のスナップショットとして持つ設計では、この導線が書けません。複製にすれば「Report とは何か」が版によらず同じ形になり、一覧・詳細・承認・確定のフローをそのまま再利用できると判断しました。

## 採らなかった案

- **`report_revisions` 別テーブル** — 版の一覧は取りやすいですが、明細を版ごとに編集・再承認する経路を別途作ることになり、モデルが二重化するため見送りました。
- **履歴テーブル + トリガによる自動記録** — 監査には向きますが、業務上の「修正版を作る」という明示的な行為を表現していないため見送りました。

## 修正版は空にできない

**版番号が 2 以上の Report では、明細を 0 件にできません**（最後の 1 件を削除できない）。初版は 0 件でいられます。

修正版を作った時点で旧版は `superseded` になり、「これはもう最新ではない」と宣言済みです。その後継を空にすると、確認依頼にも進めず（0 件は拒否される）、旧版へも戻れない（`superseded` からは修正版を作れない）系列が残ります。しかも空の版は営業の一覧に出ないので、**誰にも見えないまま止まります**。破綻ではなく沈黙して止まる形なので、運用としては最も気づきにくい壊れ方です。

初版が 0 件でいられるのは、まだ誰にも何も約束していないからです。この非対称は「宣言の前か後か」で説明できます。全ての明細を差し替えたい場合は、先に追加してから削除します。

## 並走の防ぎ方は 2 段

作成前にアプリ側が進行中の版を読んで `RevisionAlreadyInProgress` を返します。その判定と INSERT の間に他の版が割り込んだ場合は、部分ユニークインデックスが止めます。**DB の拒否は 500 にせず、同じ `RevisionAlreadyInProgress` に写して 409 で返します。** 制約違反をそのまま出しても利用者には何も伝わりません。

## 影響

- `unique(series_id, version)` で版番号の重複を防ぎます。
- **`series_id` に対して進行中（`draft` / `in_review`）の版は最大 1 つ**、を部分ユニークインデックスで強制します。同じ系列に修正版が 2 つ並走する事故を DB で止めるためです。
- 書き込みの順序が固定されます。新しい版を先に INSERT しないと、旧版を `superseded` にする UPDATE をトリガが拒みます（[ADR-0008](./0008-immutability-enforced-in-two-layers.md)）。
- 閲覧の判定を系列単位へ広げます（[ADR-0010](./0010-sales-owner-lives-on-the-line.md)）。版の履歴のリンクが必ず踏めるようにするためです。
- 系列をまたいだ集計（取引先ごとの月次合計など）では、`superseded` を除外し最新の確定版のみを見る、という条件を毎回書くことになります。ビューを 1 枚用意して隠します。
