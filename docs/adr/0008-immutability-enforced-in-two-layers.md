# 確定後の不変性はアプリ層と DB 層の二重で強制する

Confirm 済みの Report とその ReportLine は変更できません。これをドメイン層の遷移関数 1 箇所で守るだけでなく、PostgreSQL 側でも `confirmed` な行への UPDATE / DELETE を拒否します。アプリ層のバグや、将来追加される別経路の書き込みでも不変条件が崩れないことを、データ層まで下ろして保証するためです。

深掘り領域が版管理＝不変性である以上、「そう書いた」ではなく「そうとしか動かない」ことを示せる形にしたいと考えました。

## 採らなかった案

- **アプリ層のみ** — 実装は速いですが、保証はコードレビューの注意力に依存するため見送りました。
- **確定時に別テーブルへスナップショット** — 不変性は得られますが、Revision で明細が版ごとに再編集・再承認される導線（[0007](./0007-approval-is-bound-to-content.md)）と噛み合いません。スナップショットは読み取り専用の塊であって、次の版の編集起点にならないため見送りました。

## 影響

- Drizzle のマイグレーションに生 SQL のトリガを 1 本足します。Drizzle のスキーマ定義だけを読んでも不変条件が見えないので、その旨をスキーマ側にコメントで残します。
- 確定済み Report の修正は、内容の書き換えではなく Revision の作成としてのみ可能になります。
