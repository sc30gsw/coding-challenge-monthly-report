# 業務上の失敗は例外ではなく `better-result` の Result で表す

**決定:** 「確定済みなので編集できない」「未承認の明細が残っている」といった遷移拒否は `Result` + `TaggedError` で返します。throw しません。プログラマの欠陥（不変条件違反）だけ throw / Panic のままにします。

## なぜ

記述と分岐の書き方を一定のルールに揃え、コードの品質を揃えるためです。遷移拒否を型に載せると、UI の「なぜ確定できないか」が文字列マッチになりません。better-result の `TaggedError` には未承認件数や差し戻し理由もフィールドとして載せられるので、文言のパースではなくエラーそのものが非活性理由になります。あわせて、想定内の失敗（業務上の拒否）とバグ（不変条件違反）が混ざらなくなると判断しました。throw にすると握り潰しても型検査を通り、品質の揃えようがなくなります。

## 採らなかった案

- **例外を投げる** — 短いですが、失敗の種類がシグネチャに現れず、呼び出し側の書き方が揃わないため見送りました。
- **`{ ok, error }` の自前ユニオン** — 依存は減りますが、合成と網羅を自前で書くことになり、ルールがまた割れるため見送りました。

## 影響

- `LinesNotFullyApproved` / `ReportHasNoLines` / `RevisionAlreadyInProgress` などが、UI の非活性理由と拒否の文言にそのまま使えます。文言はドメイン層が持ち、クライアントで訳し直しません。
- 失敗の網羅は `matchError` が保証します（`src/server/http-failure.ts`）。拒否の種類を増やすと、HTTP へ写す箇所が型エラーになります。

### 実装で分かったこと

- **`Result.gen` / `yield*` は使っていません。** 当初は多段チェックを直線に書く手段として見込んでいましたが、実際の遷移関数は「条件を満たさなければ理由つきで即座に返す」の連なりで、判定の**順序そのものが業務ルール**でした（例: 修正版は状態を先に見てから並走を見る）。早期 return のほうが、その順序が読んだとおりに残ります。
- **プロセス境界で `Result.serialize` / `deserialize` は使っていません。** ここでの境界は HTTP で、HTTP には既にステータスコードという失敗の語彙があります。その上に Result の封筒を重ねると、エラーの表現が 2 つになり、OpenAPI からも読めなくなります。サーバーは `matchError` でタグをステータスへ写し、本文は `{ message, tag }` の平objectで返します。クライアントは `toResult`（`src/lib/api/result.ts`）でそれを `Result` に組み直します。**タグは境界を越えても保存される**ので、当初の狙い（理由が型に載る）は満たしています。
- クラスのインスタンスは境界を越えません。越えるのはタグと文言だけです。
