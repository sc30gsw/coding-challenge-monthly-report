# 月次報告書 共同作成アプリケーション

このアプリは、管理者と営業が取引先ごとの月次報告書を共同で仕上げる社内アプリです。明細書を 1 枚ずつやりとりし、確定まで進めます。

基本要件に加え、提出書類と修正版を辿るための項目を持たせています。基本要件だけでは、確定後も中身が残ることと、版を辿ることが書けないためです。

表紙に持たせたものは、次の 4 つです。

- **宛先** — 提出当時の宛名を残すため。台帳だけを見ると、社名変更で確定済みの表示が書き換わります
- **系列** — 別物である初版と修正版を、あとから辿るための印です。修正版は実質別の報告書です。例えば、この印がないと「ミドリ工業の 2026-07 を作り直したもの」だと分からないため、旧版を辿ることができなくなります
- **版番号** — 辿ったときに、何版目かを表すため
- **確定日時** — いつ締めたかを残すため

明細に持たせたものは、次の 2 つです。

- **直近の差し戻し理由** — 直している最中も「なぜ差し戻されたか」が見えるようにするため。理由のない差し戻しは作れないようにしています
- **表示順** — 明細の並びを保つため。（※ UI上でソートする操作は、実装していません）

図は [docs/design.md](docs/design.md) の「データモデル」にあります。

## 設計判断

**設計の核は、確定した報告書を提出書類として扱うことです。** 提出書類の中身は、確認した内容のまま残ります。共同作成と修正版を両立させるため、**状態・権限・データの三層**で同じ約束を守るような設計としています。

### 状態

**状態は、報告書と明細で分けています。** 報告書が表現するのは「この 1 枚は、いまどこまで進んだか」という全体のステータス（状態）です。明細が表現するのは、各明細についての営業担当者が提示するステータス（状態）です。1 枚の中で、ある行は「これでよい」、ある行は「直してほしい」、ということが同時に起きるシステムとなっているため、このように各ステータスを報告書と明細で分けています。

報告書の状態は **下書き → 確認中 → 確定済み → 旧版**の **4 つ**です。明細の状態は **未確認 / 承認済み / 差し戻し**の **3 つ**です。

**差し戻しは、報告書の状態ではありません。** 1 枚の中で、行ごとに営業の返答・状態が異なります。報告書を「差し戻し」にすると、通った行まで差し戻されたように見えてしまいます。

例）確認中の報告書に明細が 2 行あり、佐藤さんの担当行は承認済・鈴木さんの担当行は金額が違うため差し戻し、という場合
この場合に、報告書全体を「差し戻し」にすると、佐藤さんから見ても自分の行まで差し戻されたように見えてしまいます。
実際は佐藤さんの行は承認済みで通っています。そのため、報告書は確認中のまま、差し戻しは鈴木さんの行だけに据え置くようにしています。

**確認中から下書きへ戻す操作（取り下げ）は作っていません。** 差し戻された行は、報告書を確認中のまま直すことができます。下書きに戻してから直す、というもう一つのやり方は置いていません。

例）鈴木さんが差し戻した行を、管理者が金額ごと直す場合
この場合に、いったん下書きへ戻すと、鈴木さんの一覧から消えたり、「まだ依頼されていない」ように見えたりします。
実際は同じ直しなので、報告書は確認中のステータスのまま金額を直すことができるようにしています。鈴木さんには、直しの間も「確認中・差し戻しあり」と表示し続けることができます。

**承認は、行ではなく、その時点の内容に紐づきます。** 営業が見た金額と、提出される金額が同じでなければ、承認の意味がなくなります。未確認の状態に戻せるのは管理者だけです。しかも、明細の金額・案件名・担当営業を編集したときです。営業が自分で戻す操作はありません。

例）佐藤さんが 100 万円の行を承認したあと、管理者が同じ行を 1,000 万円に書き換える場合
この場合に、該当する明細が承認のステータスのままだと、佐藤さんは 100 万円の認識なのに、提出されるのは 1,000 万円となり、承認済みのままなので、確定もできる可能性が生まれます。
実際は佐藤さんが見た内容と、提出される内容に差異があるため、編集したら未確認に戻すようにします。したがって、佐藤さんは、直った 1,000 万円をもう一度承認する必要があるという設計にしています（[ADR-0007](docs/adr/0007-approval-is-bound-to-content.md)）。

**確認できるのは、未確認の明細だけです。** 承認は「この内容でよい」という意思表示です。中身が変わっていないのに、状態だけ動いてはいけません。

例）佐藤さんが承認した翌日、金額も案件名も一度も変わっていないのに、気が変わって自分で差し戻したい場合
この場合に、自分で差し戻せると、承認は「この数字でよい」ではなく、「今の気分で付け外しできる印」になります。
実際、中身は変わっていないので、営業が承認や差し戻しできるのは、未確認の行だけです。未確認の状態に戻せるのは管理者かつ、明細の金額・案件名・担当営業を編集したときのみです。営業が自分で戻す操作はありません。

**確定できるのは、明細が 1 件以上あり、かつ全明細が承認済みのときだけです。** 「全部承認済みか」だけを見ると、明細が 1 行もない報告書も通ってしまうため、このような設計としています（[ADR-0012](docs/adr/0012-confirm-preconditions.md)）

### 権限

**誰が何をしてよいかは、画面のボタンではなく、API側の処理が毎回判定します。** ボタンを隠すなどUI上の表示変更でなくAPI側でも判定を行います。

**「自分に関係する報告書」は、明細の担当から決めます。** 報告書側には担当営業を持たせず、明細に紐づくようにしています。

**営業は、報告書全体を読めますが、操作できるのは、自分の担当明細だけです。**

**どれか 1 版でも担当したことがあれば、その系列のすべての版の詳細を開けます。**

例）佐藤さんが第 1 版の担当で、修正版（第 2 版）の担当が鈴木さんに付け替わった場合
この場合に、第 2 版の担当だけで詳細を開けるかを決めると、佐藤さんは第 1 版の画面で「第 2 版を見る」というリンクを押した先でアクセスが拒否されます。
実際は第 1 版を残している以上、第 2 版も開けられる状態が望ましいです。そのため、どれか 1 版でも担当したことがあれば、第 1 版も第 2 版も詳細を開けます。

**一覧に出すのは、いま担当している版だけです。**

例）上記と同じく、佐藤さんの担当は第 1 版（旧版）だけで、第 2 版の担当は鈴木さんの場合
この場合に、詳細と同じく系列の全部を一覧に出すと、佐藤さんの一覧に「いま確認しなくてよい旧版」や「担当を外れた第 2 版」が混ざります。
実際は一覧は、いま確認するものを出す場所です。そのため、一覧にはいま担当している版だけを出します。

**条件を満たしていないボタンは消さず、非活性とし、非活性の理由を出すようにしています。** 操作を止めるのは API 側の役割となっています。

### データ

**金額合計はDBに保存しません。** 合計は、明細から計算できる情報のためです。

**取引先名と宛先は、報告書へコピーします。**

例）確定済みのあと、取引先台帳の社名が変わった場合
この場合に、表示のたびに台帳を見ると、確定済み報告書の社名まで書き換わります。
実際は提出当時の名前が残っていてほしいです。そのため、作成時に報告書へコピーします（[ADR-0014](docs/adr/0014-client-master-with-copied-cover-fields.md)）。

**修正版は、履歴の記録ではなく、新しい報告書です。**

例）確定済みを読み取り専用のコピーとして残し、そのコピーの上では差し戻しできないようにした場合
この場合に、修正版で営業が「直してほしい」と言えません。
実際は修正版でも、初版と同じように直して再承認する必要があります。そのため、報告書と明細を丸ごと複製した新しい報告書にします。辿る印が系列、順番が版番号です（[ADR-0009](docs/adr/0009-revision-is-a-copied-report.md)）。

**確定済みの金額や明細は、アプリからもDBからも書き換えられません。** 直したいときは修正版を作るという基本要件を遵守します。

## 深掘りした領域：確定後の修正版

「元の版を残して修正版を作る」は、操作としては 1 つですが、難しいのは、**その周りで業務が止まらないようにすること**です。
そのために、工夫した点は以下の **4 つ**です。

### 1. 新しい版を先に作り、そのあと元の版を旧版にする

修正版を作るときは、次の順で一度に行います。

1. 新しい版を作る
2. 明細をコピーする
3. 元の版を旧版にする

**元の版を先に旧版にはできません。** 新しい版があるときだけ、元の版を旧版にできます。

例）先に「確定済み」を「旧版」にしてから、新しい版を作ろうとする場合
この場合に、新しい版がまだないので、データベースが「旧版にする」操作を拒否します。先に旧版にできてしまうと、新しい版を作らずに確定済みを消したことにできてしまうためです。

### 2. 作業中の修正版は、同じ系列に 1 つだけ

**同じ系列に、作業中の修正版は 1 つだけです。** 2 つあると、どちらを直せばよいか分からなくなるためです。

例）管理太郎さんと、もう一人の管理者が、同じ確定済みから同時に修正版を作ろうとする場合
この場合に、アプリが「作業中の修正版はない」と確認した直後に、もう一人が割り込めます。
実際は作業中の修正版は 1 つだけです。そのため、アプリが見たあと、データベースでも 2 つ目の修正版を作る操作を止めます。2 つ目の修正版を作ろうとしてデータベースに弾かれたときは、「すでに修正版がある」と返すようにしています。この同時作成も、テストで実際に起こし、担保しております（[`src/server/revisions.test.ts`](src/server/revisions.test.ts)）。

### 3. 「壊れる」より「黙って止まる」ほうを潰した

修正版の明細を全部消すと、その系列が止まり、確認依頼に進めなくなります。これは、0 件の場合に、拒否されるためです。
この場合には、旧版へも戻ることができません。旧版からは修正版を作れないためです。
また、空の版は営業の一覧に出ず、**誰の一覧にも出ず、次の操作もできません。** したがって、これはエラーになるのではなく、静かにアプリケーションが使えなくなる事象となるため、この事象を防ぐという判断をしました。

### 4. 閲覧できる範囲を、1 つの版から系列全体へ広げた

**どれか 1 版でも担当したことがあれば、その系列のすべての版の詳細を開けます。** 一覧に出すのは、いま担当している版だけです。

例）修正版で担当が佐藤さんから鈴木さんに付け替わった場合
この場合に、版ごとに「見えてよいか」を判定すると、佐藤さんは版の履歴のリンク先で拒否されます。「担当を外れた」のか「まだ明細が入っていない」のかを確かめられません。
実際は旧版を残す以上、リンクは踏めてほしいです。そのため、詳細は系列のすべての版を読めます。一覧には、いま担当している版だけを出します（[ADR-0010](docs/adr/0010-sales-owner-lives-on-the-line.md)）。

- **Tailwind** — 部品の外側の配置だけに使う

将来の拡張性は、今の幅を自作しないことの次に来る利点です。詳細は [ADR-0003](docs/adr/0003-mantine-with-tailwind-preset.md) です。

## AI ツールの利用

要件・機能の整理と技術選定は、先に自分で下書きしました。その下書きを Matt Pocock/skills の Grill-driven development（[`/grill-with-docs`](https://www.aihero.dev/skills-grill-with-docs)）で詰めるという手法を採用しました。使ったツールは **Claude Code・Cursor** です。作業ごとの分担は次のとおりです。

### 要件・設計・技術選定

- **どのツール:** Claude Code
- **どの作業:** 状態・権限・データの解釈と、技術選定の壁打ち
- **どの程度:** 下書きの作成と更新された文書の確認は人間が行っています。AI が質問と推奨を出すため、採用するかどうかは、人間が判断します。

### 決定の記録・用語集（`CONTEXT.md`）

- **どのツール:** Claude Code
- **どの作業:** 問い詰めて固まった判断の文書化と、文言の修正
- **どの程度:** 残す内容の判断は私が行いました。文章の下書きは AI で、文書の確認は私が実施しました。

### 実装

- **どのツール:** Claude Code・Cursor
- **どの作業:** 機能の実装
- **どの程度:** テストを先に書いてコードを書くのといったTDD（テスト駆動開発）は Claude Code が主導し、改善・整理・不具合解消・ドキュメントの整合性確認は Cursor が主導するよう使い分けました。私は[チケット](https://github.com/sc30gsw/coding-challenge-monthly-report/issues)の確認と指示および、**承認確認・承認の通す・拒否するといった判断**を行いました。

### レビュー

- **どのツール:** Claude Code
- **どの作業:** 実装後のコードレビュー
- **どの程度:** 一次レビューは Claude Code です。私は動作確認と、指摘を採るか否かの判断、AI レビュー後の見直しを実施しました。

## 作らなかったこと・時間があれば足したいこと

意図的に作らなかったものは **3 つ**です。

- **E2Eテスト** — CIの安定性と戦略として画面側はテスティングトロフィー、API層はテストピラミッドを採用したため、現時点でなくても品質を担保できると判断しました
- **表紙の編集** — 版管理より優先度が低いと判断しました。取引先を変えるのは、別の報告書を作るのと同じあるため、対象月と宛先の訂正だけを許す画面は、今回の深掘りでは不要と判断しました。また、直したい場合は、下書きのうちに作り直すことで対応できるため、意図的に作成対象からは除外しました。
- **通知** — 状態・権限・データの設計が最優先で行われ、実装されるべきものであるため、外しました。確認依頼が出たことに営業が気づく手段は、アプリ内の一覧しかないため、この最小設計・実装後に優先される機能という認識です。

時間があれば足したいものは、次の **5 つ**です。

- **通知** — 確認依頼・差し戻し・確定を担当者に届ける
- **記録** — 状態が変わった地点で「誰が何をしたか」のログ、および監査・エラーログを残す処理。AI に実装させる比率が高いほど、後から追える価値が上がります。今回は入れていませんが、候補は [evlog](https://www.evlog.dev/) が良いと考えています（AI駆動開発前提で設計されているためです）
- **一覧の絞り込み・並べ替え** — 取引先や状態で絞れないため、系列が増えると探しにくくなることが予想できます
- **明細の並べ替え画面** — 表示順は持っていますが、画面から動かせないため
- **系列をまたいだ集計** — 取引先ごとの月次推移です。旧版を毎回除くことになるので、そのための見方を 1 枚用意するつもりでしたが（[ADR-0009](docs/adr/0009-revision-is-a-copied-report.md)）、最優先ではないため、実施していません。

## おおよその作業時間

作業時間は **約 8〜9 時間**です。内訳は、設計 2〜3 時間と、実装・テスト・文書 6 時間です。

実装の時間は、コミット履歴で追えます。最初のコミットから最後まで約 6 時間です。その前に、要件の解釈・状態と権限の設計・技術選定の壁打ち・決定記録の執筆に 2〜3 時間かけています。時間配分としては、**手を動かす前の設計に 3 分の 1 を使った**形です。

## セットアップ

動かす前に、**Node.js**・**Vite+**・**Docker Desktop** が入っていることが前提です。入っていなければ、次の公式手順で入れるようにしてください。

### 必要なもの

必要なものは **3 つ**です。

- **Node.js** — バージョンは 24 系です（[`.node-version`](.node-version) は 24.17.0）。
- **Vite+** — `vp` コマンドです。入れ方は [Getting Started](https://viteplus.dev/guide/) です
- **Docker Desktop** — PostgreSQL の起動に使います。コマンドだけではなく、デスクトップアプリを入れてください

#### Node.js の導入方法

手順の元は [Node.js のダウンロード](https://nodejs.org/ja/download) です。
※ 以下はnvmの場合のインストールコマンドですが、最新の手順は公式ページを確認するようお願いします

```bash
# nvm を入れる
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.6/install.sh | bash

# 今のシェルで nvm を読み込む（シェルを開き直す代わり）
. "$HOME/.nvm/nvm.sh"

# Node.js 24 を入れる
nvm install 24
```

入れたあとは `node -v` で 24 系が出ることを確認してください。Windows は [Node.js のダウンロード](https://nodejs.org/ja/download) から入れてください。

#### Vite+ の導入方法

[Getting Started](https://viteplus.dev/guide/) に従ってください。
※ 以下はインストールコマンドですが、最新の手順は公式ページを確認するようお願いいたします。

macOS / Linux:

```bash
curl -fsSL https://vite.plus | bash
```

Windows (PowerShell):

```powershell
irm https://vite.plus/ps1 | iex
```

入れたあと、新しいシェルで `vp help` を実行して確認してください。

#### Docker Desktop の導入方法

[Docker Desktop](https://docs.docker.com/desktop/) のアプリを入れる必要があります。コマンドだけでは不足があるため、入れたあと、アプリを起動しておいてください。
※ 最新の情報は公式ページを確認するようお願いいたします。

### 環境構築
```bash
git clone https://github.com/sc30gsw/coding-challenge-monthly-report.git
cd coding-challenge-monthly-report
vp run setup
vp dev
```

`vp run setup` が行うのは次の **4 つ**です。何度実行しても壊れません。

1. `.env.example` から `.env` を作り、`COOKIE_SECRET` を `openssl` で生成して埋める
2. `vp install`
3. `docker compose` で PostgreSQL を起動し、起動確認が通るまで待つ
4. アプリ用とテスト用の両方の保管庫に、定義の適用と見本データを流す

環境変数は [`.env.example`](.env.example) に、それぞれ何のために要るのかと併せて書いてあります。実際の値は含めていません。

### API仕様書

`vp dev` を起動した状態で **<http://localhost:5173/api/openapi>** を開いてください。画面で全APIの仕様を参照できます。

> ポート番号は `vp dev` の出力をご確認ください。既に埋まっていると別の番号で起動されるためです。

### うまくいかないとき

| 症状                                         | 対処                                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `docker compose up` がポート 5432 で失敗する | 別の PostgreSQL が動いています。停止するか、`docker-compose.yml` の `ports` を `"5433:5432"` などに変え、`.env` の 2 つの URL のポート番号も合わせてください |
| `COOKIE_SECRET` が空のまま起動して落ちる     | 既に `.env` があると `vp run setup` は上書きしません。`openssl rand -base64 32` の出力を `.env` に入れてください                                             |
| `vp test` がDBに繋がらない               | テストは `TEST_DATABASE_URL` を使います。`vp run db:up` で起動しているかご確認ください                                                                       |
| データを触りすぎて元に戻したい               | `vp run seed`。既存を消してから入れ直すので、何度実行しても同じ状態になります                                                                                |
| 完全にやり直したい                           | `vp run db:down` のあと `docker volume rm coding-challenge-monthly-report_postgres-data`、そして `vp run setup`                                              |

## コマンド

よく使うコマンドは次のとおりです。`pnpm` / `npm` は直接使いません。部品の追加も `vp add` を通してください（[AGENTS.md](AGENTS.md)）。

| コマンド             | 用途                                              |
| -------------------- | ------------------------------------------------- |
| `vp run setup`       | clone 直後の一括セットアップ（上記の 4 つ）       |
| `vp dev`             | 開発用の起動                                      |
| `vp build`           | 提出用のビルド                                    |
| `vp check`           | 形式・検査・型の確認（`--fix` で自動修正）        |
| `vp test`            | テスト（Docker の PostgreSQL が起動している前提） |
| `vp run db:reset`    | 保管庫の起動 → 定義の適用 → 見本データをやり直す |
| `vp run db:up`       | PostgreSQL の起動のみ                             |
| `vp run db:down`     | PostgreSQL の停止                                 |
| `vp run db:generate` | 定義から変更手順を生成                            |
| `vp run db:migrate`  | 定義の適用のみ                                    |
| `vp run seed`        | 見本データの投入のみ（何度実行しても同じ結果）    |
| `vp run fallow`      | 使っていないファイル・部品・公開口の検出          |
| `vp run doctor`      | 画面向けの健全性チェック                          |
