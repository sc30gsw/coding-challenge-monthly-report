# 月次報告書 共同作成アプリケーション

管理者と営業が、取引先ごとの月次報告書を共同で仕上げる社内アプリ課題です。1 枚ずつやりとりし、確定まで進めます。

**深掘り領域: 確定後の修正版フロー（版管理）**

確定済みの報告書は不変です。元の版を残し、修正版を作り直します。この流れが崩れないよう、状態・権限・DB 制約の三層で守っています。

状態・権限・データモデルの判断は、次のドキュメントにまとめています。README には技術選定の理由と、設計の要点だけを書きます。

## 設計判断（状態・権限・データモデル）

本課題の核です。図と全パターンは [docs/design.md](docs/design.md) にあります。ここには**何をどう決め、なぜそう決めたか**を書きます。

### 状態をどう置いたか

報告書は `draft → in_review → confirmed → superseded` の 4 つです。明細は `pending / approved / changes_requested` の 3 つです。

**差し戻しを報告書の状態にしていません。** 1 枚の中に、承認済み・差し戻し・未確認は同時に存在します。報告書に 1 つのスカラーを置くと、この混在を表せません。差し戻しは明細の状態です。報告書は「確認中」のままにします。

**`in_review → draft`（取り下げ）も作っていません。** 差し戻し対応の編集は `in_review` のまま行えます。戻す遷移を足すと、経路が 2 つになります。「戻して直して、また依頼する」と「そのまま直す」です。営業から見た報告書の見え方が、管理者の操作次第で変わります。

**承認は行ではなく「その時点の内容」に紐づきます。** 管理者が承認済み明細を編集すると、その明細は `pending` に戻ります。承認を行に貼ったままだと、次が成立します。「営業が承認 → 管理者が金額を書き換え → 全明細承認済みなので確定できる」。提出書類として破綻します。差し戻し対応で編集を重ねるほど確定は遠のきます。それは業務として正しい遠のき方です（[ADR-0007](docs/adr/0007-approval-is-bound-to-content.md)）。

**確認できるのは未確認の明細だけです。** 営業は、一度承認した行を自分で差し戻せません。その逆もできません。未確認へ戻せるのは、管理者の編集だけです。営業が確認状況を往復できると、内容が一度も変わっていないのに状態だけが動きます。承認が「その時点の内容への意思表示」でなくなります。

**確定の条件は「明細 1 件以上 かつ 全明細が承認済み」** です。「すべて承認済み」は、明細 0 件のとき自動的に真になります。件数を別に見ないと、空の報告書が不可逆に確定します（[ADR-0012](docs/adr/0012-confirm-preconditions.md)）。

### 権限をどう置いたか

判定は Elysia の macro 1 箇所を通ります。そこから **報告書単位 → 明細単位** の 2 段でかかります。前者を通っても、後者で弾かれる経路があります。

**「自分に関係する報告書」は明細から導出します。** 報告書側に担当営業を持たせて非正規化していません。同じ事実を 2 箇所に持つと、明細の担当を付け替えたときに必ずずれます（[ADR-0010](docs/adr/0010-sales-owner-lives-on-the-line.md)）。

**営業は報告書を全体として読めます。操作できるのは自分の担当明細だけです。** 自分の行だけに絞ると、金額合計や他の明細が見えません。見えないまま承認することになり、確認の意味が痩せます。

**閲覧の判定だけは系列単位です。** 版ごとに判定すると、版の履歴のリンク先で拒否されます。修正版で担当が付け替えられた場合に実際に起こります。営業は「担当を外れた」のか「まだ明細が入っていない」のかを確かめられません。一覧は「いま自分が確認すべきもの」を出す場所です。担当明細を含む版だけに絞ったままです。

**UI の非活性化は表示の都合であって防御ではありません。** 拒否の保証はサーバー側にしかありません。押せないボタンは消さず、代わりに理由を出します。ユーザーが知りたいのは「押せるか」ではありません。「あと何をすれば前に進めるか」です。

### データモデルをどう置いたか

**金額合計は保存しません。** 明細から都度算出します。保存すると「明細を直したのに合計の更新を忘れる」経路が増えるだけです。確定後は明細が不変なので、算出結果も不変です。

**取引先名と宛先は報告書へコピーします。** マスタを FK で引くだけにすると、取引先の社名変更で確定済み報告書の表示が書き換わります。不変性の一番わかりにくい違反経路です（[ADR-0014](docs/adr/0014-client-master-with-copied-cover-fields.md)）。

**修正版は履歴テーブルではありません。** 報告書と明細を丸ごと複製した、新しい報告書です。系列は `series_id`、順序は `version`。明細は版ごとに再編集・再承認されます。読み取り専用のスナップショットでは、差し戻しの導線が書けません（[ADR-0009](docs/adr/0009-revision-is-a-copied-report.md)）。

**確定後の不変性はアプリ層と DB トリガの二重で守ります。** 「そう書いた」ではなく「そうとしか動かない」形にするためです（[ADR-0008](docs/adr/0008-immutability-enforced-in-two-layers.md)）。

## 業務ルールの堅牢さをどう検証したか

宣言したルールが実際に崩れないことを、3 つの層で確かめています。テストは 20 ファイル・206 件です。

| 層                                 | 何を守るか                                    | 例                                                                                                                                             |
| ---------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ドメイン単体（DB なし）            | 状態 × 操作 × ロールの全組み合わせ            | [`confirmation.test.ts`](src/features/reports/domain/confirmation.test.ts), [`revision.test.ts`](src/features/reports/domain/revision.test.ts) |
| API 統合（実 PostgreSQL）          | 画面を経由しない要求。認可・入力検証・DB 制約 | [`reports.test.ts`](src/server/reports.test.ts), [`revisions.test.ts`](src/server/revisions.test.ts)                                           |
| フロント統合（API をモックしない） | 画面 → API → DB の一本                        | [`report-line-table.test.tsx`](src/features/reports/components/report-line-table.test.tsx)                                                     |

要点は 3 つです。

- **API のテストは画面を通りません。** 営業が他人の明細を承認する要求、確定済み報告書への更新要求を、Cookie を差し替えて直接投げています。UI にボタンが出ていないことは防御ではありません。その経路でしか意味を持ちません
- **DB トリガは、アプリが決して発行しない書き込みで試しています**（[`immutability.test.ts`](src/db/immutability.test.ts)）。アプリ層のバグを想定した最後の砦です。アプリ経由で試しても意味がありません
- **フロントは API をモックしません。** `fetch` をインプロセスの Elysia アプリに向けています。クライアントをスタブすると、サーバーが変わってもテストが緑のままになります。この層を置く意味が無くなります

修正版の並走を DB が止める経路も、実際に踏ませています。コミットしないトランザクションを握ったまま、`pg_stat_activity` でロック待ちを待ちます。時間で待つと不安定になるためです。

## 深掘りした領域：確定後の修正版フロー（版管理）

「元の版を残して修正版を作る」は、機能としては 1 本の API です。難しいのは**その周りで業務が止まらないようにすること**でした。工夫した点を 4 つ挙げます。

### 1. 書き込みの順序に業務ルールを埋めた

修正版の作成は 1 トランザクションです。順序は次のとおりです。

1. 新しい版を INSERT
2. 明細を複製
3. 元の版を `superseded` に UPDATE

この順序でしか通りません。DB のトリガが `confirmed → superseded` を許す条件を、「**同じ系列により新しい版が既に存在すること**」にしてあるためです。

逆順を許すと、「後継を作らずに確定済みを無効化する」経路が空きます。順序をコメントで注意喚起するのではありません。守らなければ動かない形にしました。

### 2. 並走を 2 段で止め、DB の拒否を「理由」に翻訳した

同じ系列に修正版が 2 つできると、どちらが正なのか決まりません。アプリ側で事前に進行中の版を読み、`RevisionAlreadyInProgress` を返します。ただし**その判定と INSERT の間には窓が開きます**。そこは部分ユニークインデックスが塞ぎます。制約違反を同じタグに写して 409 で返します。500 は出しません。

この経路は、テストで実際に踏ませています。コミットしない版を握ったまま、`pg_stat_activity` でロック待ちを待ちます（[`src/server/revisions.test.ts`](src/server/revisions.test.ts)）。「たぶん動く防御」を残さないためです。

### 3. 「壊れる」より「黙って止まる」ほうを潰した

修正版の明細を全部消すと、系列が止まります。確認依頼にも進めません（0 件は拒否）。旧版へも戻れません（`superseded` からは修正版を作れない）。しかも空の版は営業の一覧に出ません。**誰にも見えないまま止まります。** 破綻ではなく沈黙です。運用では最も気づきにくい壊れ方です。

版番号が 2 以上の報告書では、明細を 0 件にできないようにしました。初版が 0 件でいられるのは、まだ誰にも何も約束していないからです。

### 4. 閲覧の判定を報告書単位から系列単位へ広げた

旧版を残す設計は、辿れなければ意味がありません。版の履歴にリンクを出す以上、それが踏めないと困ります。版ごとに可視性を判定すると、修正版で担当が付け替えられた営業はリンクの先で拒否されます。「担当を外れた」のか「まだ明細が入っていない」のかを確かめられません。詳細の閲覧だけを系列単位に広げました。一覧は「いま自分が確認すべきもの」に絞ったままです（[ADR-0010](docs/adr/0010-sales-owner-lives-on-the-line.md)）。

## 妥協した点・もっと時間があればやりたかったこと

### 意図的に作らなかったもの

- **E2E テスト** — 安定性の割に合わないと判断しました。代わりに、フロントの integration テストで `fetch` をインプロセスの Elysia アプリに向けています。**API をモックせずに**画面 → 認可 → DB まで通しています。クライアントをスタブすると、サーバーが変わってもテストが緑のままになります。この層を置く意味が無くなります
- **表紙の編集** — 取引先を変えるのは、別の報告書を作るのと同じです。対象月と宛先の訂正だけを許す UI は、版管理より優先度が低いと判断しました。下書きのうちに作り直します
- **通知** — 確認依頼が出たことに営業が気づく手段は、アプリ内の一覧しかありません。実運用では最初に必要になる機能です。ただし状態・権限・データの設計とは層が違うため外しました

### 時間があれば足したいもの

- **通知**（上記）。確認依頼・差し戻し・確定を担当者に届ける
- **observability** — [evlog](https://www.evlog.dev/) のような構造化ログを、状態遷移の各点に入れたいです。AI に実装させる比率が高いほど、「どこで何が起きたか」を後から追える価値が上がります。今回は入れていません
- **一覧の絞り込み・並べ替え** — 取引先や状態で絞れません。系列が増えると探しにくくなります
- **明細の並べ替え UI** — `position` は持っていますが、画面から動かせません
- **系列をまたいだ集計** — 取引先ごとの月次推移。`superseded` を除外する条件を毎回書くことになります。ビューを 1 枚用意するつもりでした（[ADR-0009](docs/adr/0009-revision-is-a-copied-report.md)）

## おおよその作業時間

**約 8〜9 時間**（設計 2〜3 時間 + 実装・テスト・ドキュメント 6 時間）。

実装フェーズはコミット履歴で追えます。最初のコミットから最後まで約 6 時間です。その前に、要件の解釈・状態と権限の設計・技術選定の壁打ち・ADR の執筆に 2〜3 時間かけています。時間配分としては、**手を動かす前の設計に 3 分の 1 を使った**形です。承認を内容に紐づけるか行に紐づけるか、修正版を複製にするかスナップショットにするかは、後から変えると全部書き直しになります。先に決め切る価値がありました。

## セットアップ

### Vite+（`vp`）のインストール

手順は [Getting Started](https://viteplus.dev/guide/) に従ってください。

macOS / Linux:

```bash
curl -fsSL https://vite.plus | bash
```

Windows (PowerShell):

```powershell
irm https://vite.plus/ps1 | iex
```

インストール後、新しいシェルで `vp help` を実行して確認してください。

### 必要なもの

- **Node.js** — [`.node-version`](.node-version) を参照
- **Vite+** — 上の手順で `vp` が PATH にあること
- **Docker** — PostgreSQL の起動に使います。デーモンを起動しておいてください

```bash
git clone https://github.com/sc30gsw/coding-challenge-monthly-report.git
cd coding-challenge-monthly-report
vp run setup
vp dev
```

`vp run setup` が行うのは次の 4 つです。何度実行しても壊れません。

1. `.env.example` から `.env` を作り、`COOKIE_SECRET` を `openssl` で生成して埋める
2. `vp install`
3. `docker compose` で PostgreSQL を起動し、healthcheck が通るまで待つ
4. アプリ用とテスト用の両方のデータベースにマイグレーションを適用し、seed を流す

Docker を使わず外部の PostgreSQL に繋ぐ場合は、`.env` の `DATABASE_URL` と `TEST_DATABASE_URL` を書き換えてから `vp run setup` を実行してください。Docker には触らず、マイグレーションだけを当てます。

環境変数は [`.env.example`](.env.example) に、それぞれ何のために要るのかと併せて書いてあります。実際の値は含めていません。

### API 仕様書（OpenAPI）

`vp dev` を起動した状態で **<http://localhost:5173/api/openapi>** を開いてください。Scalar の画面で全エンドポイントを参照でき、そのまま実行もできます。

定義は Valibot スキーマから生成しています。ルートの入力検証とこの仕様書は同じ定義を読みます。実装と仕様がずれません（[ADR-0013](docs/adr/0013-eden-treaty-with-openapi.md)）。疎通確認だけなら <http://localhost:5173/api/health> が DB の状態も返します。

> ポート番号は `vp dev` の出力をご確認ください。既に埋まっていると別の番号で起動します。

### うまくいかないとき

| 症状                                         | 対処                                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `docker compose up` がポート 5432 で失敗する | 別の PostgreSQL が動いています。停止するか、`docker-compose.yml` の `ports` を `"5433:5432"` などに変え、`.env` の 2 つの URL のポート番号も合わせてください |
| `COOKIE_SECRET` が空のまま起動して落ちる     | 既に `.env` があると `vp run setup` は上書きしません。`openssl rand -base64 32` の出力を `.env` に入れてください                                             |
| `vp test` が DB に繋がらない                 | テストは `TEST_DATABASE_URL` を使います。`vp run db:up` でコンテナが起動しているかご確認ください                                                             |
| データを触りすぎて元に戻したい               | `vp run seed`。既存を消してから入れ直すので、何度実行しても同じ状態になります                                                                                |
| 完全にやり直したい                           | `vp run db:down` のあと `docker volume rm coding-challenge-monthly-report_postgres-data`、そして `vp run setup`                                              |

### ログイン

`/login` で立場を選ぶだけです。パスワードはありません。

| 名前      | 役割   |
| --------- | ------ |
| 管理 太郎 | 管理者 |
| 佐藤 花子 | 営業   |
| 鈴木 一郎 | 営業   |

同じ報告書を 2 つの立場で見るには、ログアウトして別のユーザーを選び直してください。**佐藤と鈴木では一覧の中身が変わります**（担当する明細を含む報告書だけが出るため）。

要件が「ロールの切り替え方法は自由（ダミーログインも可）」としているため、認証基盤は入れていません。ただし選んだ `user_id` は署名付き httpOnly Cookie に入れ、**サーバーが毎リクエストで検証します**。署名を外すと、開発者ツールで書き換えるだけで他人になれます。以降の権限設計が意味を失うためです（[ADR-0015](docs/adr/0015-signed-cookie-dummy-login.md)）。

### 最初から入っているデータ

業務フローを作るところからではなく、**触るところから**始められるよう、各状態のサンプルを 5 系列入れてあります。

| 取引先     | 対象月  | 状態                     | ここで試せること                                           |
| ---------- | ------- | ------------------------ | ---------------------------------------------------------- |
| アオイ商事 | 2026-08 | 下書き                   | 明細の追加・編集・削除、確認依頼。鈴木には見えません       |
| ミドリ工業 | 2026-08 | 確認中（全明細が未確認） | 営業でログインして承認・差し戻し。コメントのやりとり       |
| シオカゼ   | 2026-08 | 確認中（差し戻し 1 件）  | 確定ボタンが非活性で理由が出ている状態。佐藤には見えません |
| アオイ商事 | 2026-07 | 確定済み                 | 編集できないこと。確定後もコメントは残せること             |
| ミドリ工業 | 2026-07 | 旧版 + 第 2 版が下書き   | 版の履歴、旧版が読めること、修正版の明細が未確認に戻ること |

`vp run seed` でいつでもこの状態に戻せます。既存を消してから入れ直すので、何度実行しても同じ結果になります。

## コマンド

| コマンド             | 用途                                              |
| -------------------- | ------------------------------------------------- |
| `vp run setup`       | clone 直後の一括セットアップ（上記の 4 つ）       |
| `vp dev`             | 開発サーバー（HMR）                               |
| `vp build`           | プロダクションビルド                              |
| `vp check`           | format + lint + typecheck（`--fix` で自動修正）   |
| `vp test`            | テスト（Docker の PostgreSQL が起動している前提） |
| `vp run db:reset`    | DB 起動 → マイグレーション → seed をやり直す      |
| `vp run db:up`       | PostgreSQL の起動のみ                             |
| `vp run db:down`     | PostgreSQL の停止                                 |
| `vp run db:generate` | スキーマ定義からマイグレーションを生成            |
| `vp run db:migrate`  | マイグレーションの適用のみ                        |
| `vp run seed`        | seed データの投入のみ（何度実行しても同じ結果）   |
| `vp run fallow`      | 未使用ファイル・依存・エクスポートの検出          |
| `vp run doctor`      | React 向けの健全性チェック                        |

`pnpm` / `npm` は直接使いません。依存の追加も `vp add` を通してください（[AGENTS.md](AGENTS.md)）。
